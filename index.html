Four ideas come up in nearly everything below:

  • Verification creates trust. An agent needs a repeatable way to prove the real app works, not just that the code compiles.

  • Context is the main limit. Performance drops as the context window fills, so keep it small and send noisy work to subagents.

  • Fix mistakes where they can't recur. A correction in chat disappears. Architecture, types, lint and CI keep working in the next session.

  • Parallelism comes last. Running more agents only helps once you trust what one agent hands back.

pstack in Claude Code

Use the pstack-claude port. It's a real Claude Code plugin that tracks poteto's original and adds automatic routing, which a plain copy of the skills doesn't. It's third-party, so read the skills before you trust them.

# Run inside Claude Code 2.1.292 or later
/plugin marketplace add michael-denyer/pstack-claude
/plugin install pstack@pstack-claude

Your first session

  1. Pick your models. Run /pstack:setup-pstack. Commands in Claude Code use the /pstack: prefix.

  2. Build verification first. Run /pstack:create-verification-skill on your main project. It generates a project skill and a feature map, so the agent can run the app and prove what it did.

  3. Fix one real bug. Give it a goal and a way to check it: /pstack:poteto-mode [the bug]. repro first, then fix and verify.

  4. Check the evidence. Look for the failing case and the passing case in the real app, not just a green build.

  5. Try to break the diff. Run /pstack:interrogate the whole branch, but skeptically. don't change anything yet. no nitpicks unless it's an actual bug or regression in behavior.

After install, a session hook sends multi-file changes, design choices and bugs with unknown causes to poteto-mode. Smaller tasks skip it, and you can turn this off in setup.

Skip for now

  • Autopilot and Orchestrate: Agents landing work unattended only makes sense after verification is solid. Orchestrate also needs the Graphite CLI.

  • Arena and swarm on everything: They run parallel agents, so they use more of your limits. Use them for hard design choices or independent slices of work.

  • Naming skills in every prompt: State the goal and how to check it, and let the playbook choose the steps.

Check it still earns its place

The engineers you've spoken to may well be right, and the upstream README already sets Opus 5.5 as a default, so it's being kept current. The risk is that vendors now warn against heavy instructions: OpenAI says overly specific skills can hinder newer models, and Anthropic's docs say old verification instructions can cause over-verification on Opus 5.

  • Keep: Checks that run and return a result, such as tests, the verification skill and CI.

  • Treat as optional: Fixed step-by-step playbooks, which you should compare against a plain prompt.

  • Refresh model settings: Rerun /pstack:setup-pstack, because a config written earlier can still pin old defaults.

  • Test it: Block 6 below runs pstack against a plain prompt on the same commit, so you can decide from your own results.

Using it in Codex

The same port installs with codex plugin marketplace add michael-denyer/pstack-claude, then codex plugin add pstack@pstack-claude. Trust its hook through /hooks. If subagents are off, set multi_agent = true under [features] in ~/.codex/config.toml.

What changes on Opus 5.5

Prompt less and set your finish line more clearly: Anthropic's Opus 5.5 playbook and prompting guide say many older habits now add noise. Published 22 September, they're the most specific material I found.

  • Start at medium effort. It's the new default, and it matched or beat Opus 5 at high in Anthropic's coding tests. Keep xhigh and max for work where you've measured a gain.

  • Give the whole task in one message. State what done means, and the one condition for stopping to ask you.

  • Delete thinking instructions. Remove lines like "think step by step", because thinking is always on. Asking it to write out its reasoning can be declined.

  • Add a stop rule to CLAUDE.md. The model can stop just to report or offer to continue. Tell it to keep going unless it's blocked or about to do something destructive, and leave this out when pair programming.

  • Keep state in a file. A TASKS.md checklist survives compaction, and it's a better progress check than the scrollback.

  • Treat subagent reports as claims. Tell the main agent to check each subagent's evidence before accepting it.

  • Narrow your reviews. Ask only for problems that would block a merge, with the file, the line and how to show it fails.

  • Use workflows for large jobs. Say "use a workflow to..." and Claude writes a script that runs many subagents. Try one directory first, as runs can use far more tokens, and watch for the warning above 25 agents.

  • Name what you don't want in UI work. Ban specific patterns, such as pill buttons or numbered section labels, rather than asking for "not generic".

If you build your own harness on the API, read the migration guide too. Forced tool choice, disabled thinking and sampling parameters all return errors or need removing.

What to build between videos

Use your main project throughout, and do each block after the video or reading it depends on. Blocks 1 to 5 are the Core path, and blocks 6 to 9 complete the Full path.

  • 1. Install pstack and build verification (2 h, after video 2). Done when the agent can launch your app and show proof of one real user journey.

  • 2. Fix a real bug (1 h). Done when you've checked the failing and passing evidence yourself and run interrogate on the diff.

  • 3. Clean your instructions (1 h, after readings 1 to 3). Delete lines like "think carefully", add a stop rule, and shorten skill descriptions. Keep checks that actually run, and remove prompts that only say "double-check your work".

  • 4. Enforce two repeated corrections (1 h, after video 3). Done when lint, types or CI fail on two mistakes you've been correcting by hand.

  • 5. Run one bounded task (0.5 h to set up). Give the whole task in one prompt with "Done means" checks, in a fresh worktree, using /goal. Don't let it merge.

  • 6. Compare pstack with a plain prompt (1.5 h). Run the same task from the same commit both ways. Compare time, usage, rework and whether the proof holds up.

  • 7. Add a hard gate and a fresh reviewer (1 h). Add a Stop hook that runs your checks, then have Codex review a Claude diff and vice versa. The cross-review is my suggestion, not an established benchmark.

  • 8. Test effort levels (1 h). Run one task at low, medium and high. Check whether a saved higher setting is costing you for nothing.

  • 9. Run a small workflow (1.5 h, after reading 6). Try use a workflow to find flaky tests in this repo: run the suite repeatedly, record which tests fail intermittently, and stop once two rounds in a row find nothing new. Check its usage, and save it if it's worth repeating.

Track accepted fixes, rework, bugs that escape and usage per accepted change. PR counts alone won't tell you whether this is working.

Key parts

  • Trust sets your throughput. Tan defines trust as an agent doing acceptable work while nobody watches. Adding agents before that point produces more bad pull requests (PRs).

  • The hardest stage is one to five agents. You babysit, correct constantly, and cannot yet see the way out.

  • Verification comes first. Agents should launch the real app, drive it like a user, and capture evidence.

  • A verification skill has two parts. A fixed command-line tool (CLI) keeps measurements consistent. A feature map tells the agent how to reach each feature.

  • Put each correction at the strongest possible layer. Prefer making the mistake impossible in the codebase. Then use static analysis. Treat rules, skills and style guides as weaker, because they can be skipped.

  • Make the shortcut the correct path. Her framework, Dune, bans code comments and blocks bad imports by checking the dependency graph.

  • Automate intake last. Bots that watch Slack or Sentry only help once the repo is worth copying.

  • Treat the numbers as self-reported. The title says 2,500 PRs and the talk says about 2,000. Neither is audited, and she says the count was never the goal.

Who should prioritize this

Watch this first if you want one compact argument for what to fix before running more agents. Skip it if you have read her pstack guide and want operating detail, because the Pocock stream and Maven lesson go deeper.

Detailed summary

This summary is based on written accounts of the talk. I did not get captions or watch the video. The main source is Redreamality's breakdown, checked against Web Reactiva, Ratstack and a Bubble's Brain PR note that records the talk's order.

The claim and its evidence

The argument is that trust produces throughput, and more agents do not. The talk was reportedly planned for Cursor Compile London and later released as a recording. The post title says 2,500 PRs shipped last month. The talk says about 2,000. Tenten reports that The Neuron counted 2,462 for August, but that count also traces back to her. Redreamality found no independent measurement.

She rejects the label software factory. She prefers a Michelin kitchen. A person stays responsible for what leaves the kitchen. The job is arranging the stove, tools, training and staffing.

The trust curve

Web Reactiva describes a chart with agent count on one axis and trust on the other. Stages run from one agent up to thousands. At one to five agents, you supervise every step. She calls this the hardest stage, partly because the exit is not visible.

Her warning is specific. Opening a hundred sub-agents or cloud agents at this stage yields regressions and bad PRs. Redreamality stresses that the hundred-agent case is a counterexample, and she does not recommend it as a setup.

Where it started: being the bottleneck

The origin was performance work on Cursor's new agents window. PRs arrived faster than she could judge whether performance was regressing. Much of her time went to Chrome DevTools: the Performance panel, traces and heap snapshots (records of memory use).

Her fix was to move that knowledge into agents. The agent would launch the app, capture a trace, find hot spots and improve them. She says the motive was removing herself as the bottleneck, and PR volume was never a target.

Verification: a CLI plus a feature map

Her first Cursor skill was internal and has no public docs. Redreamality calls it Control Glass. It uses the Chrome DevTools Protocol, an interface for controlling Chrome programmatically. It has two parts.

The first is a reproducible CLI inside the skill directory. It launches the app, collects traces and heap snapshots, and shows whether performance targets were met. Scripts that agents write on the fly drift, so a fixed tool keeps results comparable.

The second is the feature map, her own term, inspired by a sitemap. It records features, navigation paths, keyboard shortcuts and the DOM elements to click. Automations keep it current, by her description. Without it, a bug report like "a screenshot and three question marks" leaves the agent guessing.

The limit is explicit. Verification shows whether a feature works end to end. It says nothing reliable about performance targets without metrics, or about code quality. She separates correctness from quality throughout.

Quality skills: pstack

Quality needs different tools, namely skills that teach engineering judgment. Her plugin pstack packages skills drawn from her own debugging, feature work and prototyping. She gives it little time in the talk. Its entry points are /setup-pstack and then /poteto-mode, and the stated aim is writing less code, correctly.

The enforcement ladder

The most useful habit is to ask, for each correction, which layer could catch it permanently. Ratstack and Web Reactiva give this order, strongest first:

  1. Codebase and architecture. Change data structures and practices so the mistake cannot be written. She calls the codebase the agent's memory, and says anti-patterns spread like weeds.

  2. Static analysis. Use lint rules, compilers and continuous integration (CI). Her first response to tech debt is a lint rule, followed by agent cleanup later.

Detailed summary

This summary is based on the talk page's chapters and essay, plus the full transcript read through a summarizing fetch. I did not watch the video, so slides are not reflected.

The argument against specs-to-code

Pocock opens against a popular idea. In specs-to-code, you write a specification, let AI generate the code, and regenerate from a revised spec when problems appear. You never read the code. He tried it and found each regeneration produced worse code. He describes it as vibe coding under another name.

He explains why using two books. John Ousterhout's A Philosophy of Software Design defines complexity as anything that makes a system hard to understand and modify. The Pragmatic Programmer describes software entropy. Each change made without regard to the whole design makes the codebase a little worse. Every individual request can look satisfied while the system decays.

That sets up his rebuttal to the phrase "code is cheap". He says bad code is now the most expensive it has ever been, since AI output depends on the codebase it works in. His thesis follows directly. Good codebases matter more, so fundamentals matter more. He then previews a set of failure modes with a fix for each. He says there are six, but only some are explicitly numbered in the transcript.

Failure: the AI did not do what you wanted

Pocock treats this as a communication gap. The Pragmatic Programmer notes that nobody knows exactly what they want. Frederick P. Brooks's The Design of Design adds the idea of a design concept. This is the shared, invisible theory of what is being built, and it cannot live in a Markdown file.

His remedy is the Grill Me skill. It tells the AI to interview you relentlessly, walking each branch of the design tree and resolving dependencies between decisions one at a time. He says it typically produces 40 to 60 questions and he has seen up to 100. He also says the repo has about 13,000 stars. Both figures are his own.

The resulting conversation becomes a product requirements document (PRD), or goes straight into issues for an agent working away from the keyboard. He prefers this to Claude Code's default plan mode, which he says rushes to create an asset and start work. He does not reject plans. He argues they help more once shared understanding exists.

Failure: the AI is too verbose

He compares verbose responses to developers and domain experts talking past each other. The answer comes from domain-driven design and its ubiquitous language, a shared vocabulary used in code and in conversation.

He built a skill that scans a codebase for terminology and generates a Markdown file of terms in tables. Developer and AI both consult it during planning and implementation. From reading the thinking traces, he reports less verbose reasoning and implementations closer to the plan. He presents this as work in progress and offers no measured numbers.

Failure: right thing built, but it does not work

The fix is feedback loops. He lists static types, browser access for front-end work, and automated tests. He strongly recommends TypeScript and says front-end agents need a browser so they can look around.

Having loops is not enough, because the model uses them badly. It writes too much code before checking anything. The Pragmatic Programmer calls this outrunning your headlights. Your rate of feedback sets your speed limit.

TDD is his way to force small steps: write a test, make it pass, then refactor. He admits testing stays hard, because three decisions interlock. You must choose how big a unit to test, what to mock, and which behaviors to verify.

Deep modules as the enabling structure

This is where the talk connects its parts. Good codebases are easy to test, so better codebases give better feedback and better output. He returns to Ousterhout's distinction. Deep modules hide substantial functionality behind simple interfaces. Shallow modules expose many small pieces with complicated boundaries.

He says AI tends to produce shallow modules, and that they are hard for it to explore. His "improve codebase architecture" skill is a reusable multi-step process. It explores the code, finds related pieces, and wraps them in deep modules. With simple boundaries you can test through the interface, which makes TDD workable.

Failure: your brain cannot keep up

He reports feeling more tired than ever, because AI lets you ship much more code. Deep modules offer relief here too. You can treat some as gray boxes: design the interface carefully, then verify from outside rather than reviewing every line. He warns this is not advisable for critical areas such as financial logic.

Own the design

His last tip is to design the interface and delegate the implementation. Planning should explicitly cover module changes and interfaces, and he puts both in his PRDs. This keeps your mental map of the system accurate.

He cites Kent Beck's advice to invest in the design of the system every day, and argues specs-to-code divests from design instead. The AI is a tactical programmer, a sergeant on the ground. The human has to stay the strategic thinker. He closes by pointing to his skills repo and his site, AI Hero.

Detailed summary

This summary is based on the written guide, the edited essay on the talk page and the talk transcript. All examples and figures are Shihipar's own accounts of his work and his team's work.

The harness decides what you get from a model

The talk opens by saying models are grown from data, feedback and compute. Nobody designs them line by line. So the tools and prompts around a model reflect how well people understand it.

He calls the gap between what a model can do and what its setup allows "capability overhang." His example is a question about Pokémon names ending in "AW." A chat model struggles to recall them from about 1,000 names. Claude Code fetches the list, writes a filter script and runs it.

The same logic explains why Claude Code uses Bash and environment access. The model searches and builds its own context, so the whole codebase never needs to fit in the context window. He then mentions Claude Tag, a Slack-based agent, as an early proactive and multiplayer agent. It can start work without waiting for a prompt.

Update the harness when the model changes

The team removed about 80% of the Claude Code system prompt. He describes a progression: small prompts with few tools, then large prompts full of instructions and examples, then smaller prompts again.

The reasoning is that examples narrow the solution space, and the model may be more imaginative than the example. He favors supplying context over blanket prohibitions.

The ask-user-question tool shows the trend:

  • Opus 4 could barely call it reliably.

  • Opus 4.5 could run a spec interview of about 40 questions.

  • Opus 4.8 and Fable can produce a full HTML report with embedded questions.

Output followed the same path, from Markdown to plan mode to rich HTML reports. He describes this work as "closer to biology than physics." That means experimenting and watching results, since no complete rulebook exists.

Map and territory

This is the core of both the talk and the guide. The map is your prompt, spec, skills and context. The territory is the real codebase and its constraints. Whatever the map leaves out, the agent must guess.

More capable agents run longer, so they hit more decision points the map never covered. The guide says Fable is the first model whose output is limited mainly by how well he clarifies those unknowns.

He sorts knowledge into four types:

  • Known knowns: already in the prompt.

  • Known unknowns: gaps you know you have.

  • Unknown knowns: things so obvious you never write them, though you would recognize them on sight.

  • Unknown unknowns: things you have not considered, including how good a result could be.

The guide also warns about both extremes of prompting. Too specific, and the model follows instructions when it should pivot. Too vague, and it falls back on generic best practice. The key input is your context: where your thinking stands, your experience with this code and how you want to work together.

Before implementation

Blind spot pass. Ask for it using the words "blind spot pass" and "unknown unknowns." His examples are adding a provider to an unfamiliar auth module and learning color grading before grading a video. In the talk, the model also checks Git diffs and Slack for pitfalls.

Brainstorms and prototypes. These target unknown knowns, because changing requirements mid-build is expensive. Examples include a single HTML mockup with fake data, four design directions, and ten churn ideas ranked from cheapest to most ambitious. He says he has no visual taste, so he reacts to options.

Interviews. The model asks one question at a time and prioritizes answers that would change the architecture. Telling it about you, the work and the project stage improves its questions.

References. When you cannot describe what you want, point at source code, which carries more detail than screenshots. His example reads a Rust rate-limiter crate in a vendor/ folder, then reimplements its backoff behavior in a TypeScript client.

Implementation plans (guide only). Ask for a plan that leads with the decisions you are most likely to change. Those include data models, type interfaces and user-facing flows. Mechanical refactoring goes at the bottom. He recommends HTML for the plan.

During implementation

Start a fresh session and pass in the planning artifacts, such as a spec and a prototype. This gives a clean context window. Have the model keep an implementation-notes.md file. When an edge case forces a deviation, it takes the conservative option, logs it under a "Deviations" heading and continues. The log keeps judgment calls visible and teaches you for the next attempt.

After implementation

The guide suggests packaging the prototype, spec and notes into one pitch or explainer for reviewers, such as a Slack-ready document that leads with a demo GIF. For your own understanding, ask for an HTML report on the changes with a quiz. He merges only after passing it perfectly.

The guide's worked example is the Fable launch video. He asked Claude how Whisper-style transcription works and whether ffmpeg could cut filler words. He built a Remotion prototype for word-timed UI. When the footage looked muted, he asked to be taught color grading, because he could not yet define "good."

Grief, ambition and value

The last section of the talk is personal. At an earlier startup of about 30 people, he had to choose between speed work and features, because implementation took so long. Revisiting that code, work he estimated at weeks took hours.

He admits grief about losing hand-coding and holding a whole codebase in his head. He advises being "less reasonable" about inherited tradeoffs and testing whether they still hold. He built this talk's deck in about four hours with Fable.

His closing caution is that easier building does not mean more value. Value still takes many attempts and judgment.

Detailed summary

This summary is based on the page's edited essay and the full transcript, read through a summarizing fetch tool. Check exact wording against the video before quoting.

The claim under test

The talk questions the popular idea of a software factory with no human reading the code. Horthy describes the current advice as follows: spend more tokens, treat people as the bottleneck, and add adversarial review bots. The promised result is 10 to 100 times the speed with high quality.

He then lists warning signs. Mario Zechner warned at AI Engineer Europe about outages caused by coding-agent mistakes. A Faros AI report found longer review comments, more PRs merged with no review, and more incidents and bugs per developer. The essay treats these as reported warnings, not proof of causation.

His thesis follows. Critics say failures are a "skill issue", meaning users hold the tools wrong. Horthy argues the limit sits in how models are trained, so harnesses cannot fully compensate. A harness is the tooling and instructions wrapped around a model.

How factories gained loops

Horthy traces the term "software factory" to a 1968 NATO conference, then walks through a 2022 team. Work moves through a tracker such as Linear or Jira, an engineer builds it, and a PR passes checks and human review. It ships, then users and monitoring feed new work back in. Building and review each took hours or days, so teams invested in planning and architecture proposals.

Agents replace the builder and cut build time to minutes or hours. Human review then becomes the bottleneck. Teams add agent review and regression testing, then route incidents and user feedback straight into the factory. Horthy notes companies claim agents write about 75% of their code, and he treats that claim skeptically.

The end state is the "lights-off" factory, a term he credits to Dan Shapiro. Nobody reads the code. Investment shifts to testing, monitoring and rollout systems. He cites StrongDM as a reported example.

Scope and the HumanLayer experiment

Horthy limits the argument to complex existing codebases, often called brownfield. Paraphrasing Addy Osmani, he says a small side project and a decade-old enterprise system share almost no constraints. He is not arguing about vibe coding.

HumanLayer tried full lights-off in July 2025. Agents eventually hit problems they could not solve. Engineers then had to enter code they had not read for months. The site went down and users were unhappy.

His core claim is that models cannot maintain codebase quality over time without substantial human steering. He frames poor maintainability as changes in one place breaking others. He cites Martin Fowler's "shotgun surgery" smell and John Ousterhout's work on design. Models have improved at one-off tasks, he says, yet he sees little gain in codebase quality.

Why training produces the problem

Horthy attributes Claude Code's success partly to training the model against the harness it shipped. He cites revenue of about $4 billion and tentatively $9 billion within a year. The essay treats this as an anecdote. Earlier tools such as Aider and Codebuff had similar tools, including read, edit, grep and bash, but no such training.

He then explains coding reinforcement learning, where a model makes many attempts and its weights shift toward higher-scoring behavior. SWE-bench Multilingual, a common benchmark, uses roughly 15-minute tasks from repos like Redis, jq and Django. Rewards are binary: fix the issue and break nothing else.

His example is a missing nil check in fastlane, a Ruby project. The benchmark checks out the commit before the human fix and hides the reference fix and test patches. It also reverts any test edits by the agent, because models sometimes comment out tests. The patch earns reward only if old and new tests pass.

Nothing in that loop penalizes bad design. Horthy links this to needless try/catch blocks and type casts that get tests passing. The cost of bad architecture arrives months or years later, which makes it very hard to connect to one training episode.

Newer benchmarks

He sees slow progress at the frontier. SWE-Marathon uses tasks of about 400 hours by his description, such as cloning Excel's features. DeepSWE uses fresh large tasks on open-source repos. FrontierCode, from Cognition, uses multi-PR tasks, penalizes tests that do not fail on pre-patch code, and adds a judge model for quality rules.

He doubts judge models can close the gap. They can raise the floor, but they cannot exceed what reinforcement learning teaches.

What to do now

Horthy concludes that humans must keep reading code for now, and he proposes moving decisions earlier. His stages are:

  1. Product review: problem, desired behavior and mockups. Small changes can skip straight to the agent.

  2. System architecture: component contracts, data models and constraints.

  3. Program design: types, method signatures, layout and call stacks. He credits Dylan Mulroy of Cloudflare with using call graphs in planning.

  4. Vertical slices: implementation order, multi-repo coordination and checkpoints, with each stage tested. Models tend to produce horizontal plans, layer by layer, which he criticizes.

He estimates about 30 minutes of alignment can save hours of review. The essay flags this as informal.

Review overload as rework

Good PRs are easy to review, he argues, so drowning in PRs signals too many bad ones. Even 20% rework, which he calls generous for AI code, burdens both people. Model-assisted planning speeds alignment, review and coding while the team keeps reading everything and owning the code.

He closes by admitting that a world without code reading would appeal to him. He advises using loops and seeking leverage within real constraints, then pitches HumanLayer, an AI IDE and collaboration platform.

Detailed summary

This summary is based on the talk page's chapters and essay, plus the full transcript read through a summarizing fetch. I did not watch the video.

Skill hell and the missing rubric

Pocock recorded this talk because family matters kept him from attending. He describes a progression of developer traps: tutorial hell, framework hell, and now skill hell. Skills are free and easy to download. People still cannot tell good ones from bad ones, or see how they fit together. Organizations also struggle to turn operating procedures into skills an agent can run.

He says the core gap is a shared rubric. His checklist has four areas: trigger, structure, steering and pruning. He points to a skill in his repo that encodes the checklist, and he contrasts his skill set with Superpowers, another popular one.

Trigger: who bears the cost of invocation

Any skill can be invoked by a user. A model-invoked skill also places its description in the agent's context, and the agent can choose to read the SKILL.md file. He calls that description a context pointer. Setting what he calls disable model invocation to true hides it from the agent. Grill Me works this way.

Each option has a cost. Model-invoked skills add context load, since every description costs tokens on every request. A hundred skills means a hundred descriptions. User-invoked skills add cognitive load, since you must remember what exists and when to use it.

There is a third issue. The model may ignore a pointer even when the skill fits. That unpredictability forces teams to build evals (repeatable test runs) confirming skills fire at the right times. He says Superpowers is mainly model-invoked and his own skills are mainly user-invoked, which gives him more control. He accepts the extra cognitive load and does not call either approach universally better.

Structure: steps and reference

Most skills contain two kinds of content. Steps are the procedure. Reference is the information needed to carry it out.

His worked example is a PRD-writing skill, spelled "2PRD" on the talk page. It turns the current context into a product requirements document. It has three steps: find relevant context, confirm test seams with the user as a human checkpoint, then write the PRD. Its references are a definition of a test seam and a PRD template.

His rule is to make the main SKILL.md as small as possible. Smaller skills are easier to maintain and audit, and they save tokens on each use. Reference needed on every run stays inside SKILL.md, which is why this skill keeps its material inline.

Branching changes that. His domain modeling skill may update a local glossary (context.md), may create architectural decision records, or may do neither. Those templates belong in separate bundled files, each behind a conditional context pointer. The agent loads a file only when its branch applies.

Steering: leading words and leg work

Leading words are short terms that pack in a lot of meaning. Placed in a skill, they get repeated by the agent in its reasoning and output, and that repetition shifts its behavior.

His example is layer-by-layer building. Agents often work through database, schemas, API, then front end. Telling the agent not to do that is weaker than using "vertical slice" as a leading word, meaning a small end-to-end working increment expanded afterward. You check the reasoning traces to see whether the term took hold. If it does not change the plan, try stronger candidates. The agent can help brainstorm them.

Leg work is his term for the effort an agent spends on a step. He says plan mode has too little. The agent asks a few questions and then rushes to a plan, because it can see the final goal. He reports this pattern in every plan mode implementation he has tried.

His fix is phase separation. A grill-with-docs skill handles only clarifying questions, and the PRD skill handles planning afterward. The agent sees one step at a time, so hiding the future raises effort on the present. He notes that splitting every skill into phases is unnecessary. Use it where extra effort is needed.

Pruning: duplication, sediment and no-ops

A massive skill usually signals some other problem. He names three things to remove.

  • Duplication. Keep each instruction, definition and template in a single place, even across reference files.

  • Sediment. Content builds up when many contributors append to a shared file. Check whether each addition applies to every branch, move it if not, and delete stale text.

  • No-ops. These look like instructions but do not change behavior. His example is a long paragraph demanding detailed commit messages in an implement skill, when the agent would write an adequate one anyway.

The tool here is a deletion test. Remove the instruction and see whether the output changes. If it does not, the text costs context and gives nothing back. Deletion tests, plus compressing instructions into leading words, are how he keeps his skills small.

Recap

He closes with the full checklist. For trigger, check that it fires at the right times and weigh context load against cognitive load. For structure, think in branches and move branch-specific material out of SKILL.md. For steering, condense into leading words, watch for them in traces, and check leg work per step. For pruning, do a final pass for sediment, cruft and no-ops. He presents this as repeatable for your own skills and for auditing community ones.

Harness engineering and context physics

Harness engineering means tuning integration points such as commands, MCP servers, skills and codebase organization. Horthy prefers Martin Fowler's split between an inner harness, which the tool exposes, and an outer harness, which your team customizes.

He separates an information budget from an instruction budget. The first is what you retrieve. The second is how many directives and conflicts the model must juggle. Prompt injection

The harness is the code and prompts around a model. Claude Code's harness changes constantly, because each model behaves differently. Instructions added to correct one model may not carry over.

Cherny ties the 80% deletion to Opus 5. There is a timing conflict. The talk and fireside chat elsewhere in this guide, both before Opus 5 shipped, report the same 80% for Opus 4.8 and Fable. So the title figure may not be specific to Opus 5.

How to rebuild a prompt

He calls the method ablation, a term for removing a part to learn what it did. Remove the whole system prompt, then restore it line by line and measure each line like an eval (a repeatable test of model output).

The practical loop has four steps:

  1. Delete a piece.

  2. Run the real product.

  3. Watch where the model fails or excels.

  4. Re-add an instruction only after repeated stumbles on the same thing.

His reason is that the model reads every instruction on every call. Most remaining harness code, he says, handles safety, permissions, static analysis and UI. For users, he suggests deleting CLAUDE.md, skills and hooks about every six months and observing the difference.

He contrasts this with older software, which rewarded upfront architecture and large unit-test suites. Models act more like organisms with shifting personalities, so the work must be empirical. Evals saturate within about one to three model generations, and then you replace them.

Product overhang

Product overhang is what a model can do that no product exposes. Hobbling is a product getting in the model's way. Claude Code came from this idea around Sonnet 3.5, when tools offered autocomplete and read-only chat. Terminal and write access, with minimal scaffolding, let the model write whole files and features. He argues most startups are not capturing the current overhang.

Harder problems

His advice is to give tasks slightly harder than you think the model can handle. Describe the goal, guardrails and exit criteria. He gives no detailed template.

His other example is drawing. Asked to, Opus 5 can draw portraits and landscapes with OpenCV, though nobody trained it for that. He suspects many similar unasked abilities exist.

Detailed summary

What Anthropic says changed

The prompting page says Opus 5.5 generates output more than 30% faster than Opus 5. It says the model usually finishes the same task with fewer tokens. Existing Opus 5 prompts should keep working. All comparisons in this section are Anthropic's own.

  • Coding. At medium, it matched or beat Opus 5 at high on multistep repository work, with fewer steps and tokens.

Calibrating effort

The levels are low, medium, high, xhigh and max, set through output_config.effort. Level names do not map to the same amount of thinking across models. At a given level, Opus 5.5 thinks more per turn than Opus 5, especially at xhigh and max. Keeping an old setting can mean longer turns and more output tokens.

The page gives three adjustments:

  1. Raise max_tokens. It covers thinking plus the reply, even when thinking is not returned. A limit sized for Opus 5 with thinking off can truncate replies. For agentic coding, the page says 128000 has worked well. The migration guide suggests starting at 64k for xhigh or max.

  2. Reserve xhigh and max. Use them only where you have measured a quality gain.

  3. Lower effort first. Do this before adding prompt instructions meant to cut thinking.

Changing top-level effort between requests invalidates the prompt cache, the stored prefix that makes repeat requests cheaper. A per-message effort change, in beta, keeps the cache.

Unattended runs

The core problem is that some progress updates end the turn with stop_reason: "end_turn". A loop that treats any text-only turn as completion stops early. The recommended harness behavior:

  • Keep the task's parts in a checklist the model updates, through a to-do tool or a file.

  • If a turn ends with open items and no stated blocker, send a short message naming them.

  • Alternatively, state the completion condition up front and let a smaller model check each end of turn.

  • Cap automatic continuations at two or three per task, so a stuck run ends and can be reviewed.

  • If a background command or subagent is still running, wait and return its output as the next user message.

The page also offers a system prompt paragraph for fully unattended agents. It names four early stops to avoid: announcing a next step without taking it, offering to continue, listing non-blocking decisions, and stopping because a milestone arrived. It does not override confirmation for risky actions. Add it from the first request, because adding it mid-session invalidates earlier thinking blocks. Expect somewhat more tool calls and output tokens. Leave it out of human-in-the-loop applications.

Keeping users informed

The page offers four levers for visible progress:

  1. Make the client render progress-update thinking blocks. display: "updates" is in beta, with header thinking-display-updates-2026-08-18.

  2. Add a message tool for sending verbatim content mid-turn, declared from the first request.

  3. Ask in the system prompt for a one-line intent before the first tool call and a short recap at the end.

  4. Add a harness reminder after about five quiet tool-calling steps, and stop after two or three reminders.

Anthropic reports that the reminder roughly halved the share of tasks with a long silent stretch in its agentic coding tests. It reports no measurable cost change.

Coordination and time signals

Tell multi-agent teams how much time they have. Have the harness append a line such as elapsed 340s / 1200s to each message. Set the budget somewhat above the time you want spent. The model usually finishes well inside it. In Anthropic's research-task evals, budgeted teams kept quality comparable while finishing considerably faster. The budget is advisory, so keep your own hard timeout. The page warns the model may search and verify slightly less under time pressure.

For tasks across connected apps, tell the model to explore before acting, including places the request does not mention. Anthropic says this noticeably raised correct completion at both medium and max. Keep untrusted content out of what it searches, since it acts on what it finds.

Other prompting fixes

  • Settled answers. A system prompt line can stop it revisiting earlier answers. Omit it for long analyses, because it may also reduce flagging of its own mistakes.

  • Pasted text. Wrap pasted content in matching tags with a short random ID, and explain them in the system prompt. Tags can be imitated, so use this as one defense layer.

  • Dense visuals. Higher-resolution images and image tools such as PIL and OpenCV still add accuracy on the densest inputs. Re-test older scaffolding first.

  • Reasoning requests. Do not ask for reasoning in the response. Those prompts may be declined under reasoning_extraction. Read summarized thinking blocks instead.

The premise

Skills

A skill is a Markdown prompt that can be bundled with resources and scripts. Each skill's name and description load into context, so the model knows when to use it. The article lists several failure modes:

Key parts

  • Context is the constraint behind most advice. The context window holds every message, file read and command output. Performance falls as it fills.

  • Give Claude a check it can run. Without a pass or fail signal, you become the verification loop.

  • Pick how hard the check gates the stop. The options are a prompt, a /goal condition, a Stop hook, or a fresh reviewer.

  • Ask for evidence. Test output, the command run and screenshots are faster to review than re-running everything yourself.

  • Separate exploring and planning from coding. Skip the plan when you could describe the diff in one sentence.

  • Keep CLAUDE.md short. Test each line by asking whether removing it would cause mistakes. Long files make rules get lost.

  • Reset after two failed corrections. Run /clear and write a better prompt with what you learned.

  • Review in fresh context, with limits. Fresh reviewers avoid bias, but tell them to flag only correctness and requirement gaps.

Who should prioritize this

Detailed summary

Verification comes first

The guide says Claude stops when work looks done, so it needs a signal better than appearance. A useful check returns something Claude can read: a test suite, build exit code, linter, fixture diff, or browser screenshot. Run /verify yourself afterward to confirm the change against the running app.

Prompts should carry verification criteria. Give example test inputs, ask for a screenshot comparison on UI work, and ask for the root cause when a build fails.

Plan, then build

The recommended flow has four phases: explore, plan, implement, commit. Enter plan mode with Shift+Tab or claude --permission-mode plan. Press Ctrl+G to edit the plan in your editor. Planning adds overhead, so use it when the approach is uncertain, several files change, or the code is unfamiliar.

For larger features, have Claude interview you with the AskUserQuestion tool and write SPEC.md. Then start a fresh session to implement it. The guide says the best specs name files and interfaces, state what is out of scope, and end with an end-to-end verification step.

Prompts work better when they scope the task, point to sources, reference existing patterns and describe symptoms. Use @ for files, paste images, give URLs, or pipe data with cat error.log | claude -p "explain this error".

Environment

CLAUDE.md loads every session, so keep only broad rules there. Include commands Claude cannot guess, non-default style rules, test instructions, repository etiquette and known gotchas. Leave out anything readable from the code, long tutorials and file-by-file descriptions.

Maintenance tips:

  • Run /init for a starter file and /context to confirm it loaded.

  • Run /doctor on a checked-in file to get proposed cuts.

  • If Claude ignores a rule, the file is probably too long.

  • Add emphasis such as "IMPORTANT" to one line only. Emphasis on many lines loses effect.

Other extension points each have a distinct job:

  • Skills live in .claude/skills/ as SKILL.md and load on demand. Set disable-model-invocation: true for workflows with side effects you want to start by hand.

  • Hooks are scripts that always run at set points, where CLAUDE.md is only advisory. Use them for actions with zero exceptions, and browse them with /hooks.

  • Subagents in .claude/agents/ have their own context and allowed tools.

  • CLI tools such as gh are the most context-efficient way to reach external services, the guide says.

  • MCP servers (Model Context Protocol, for connecting external tools) are added with claude mcp add.

  • Plugins bundle these. Run /plugin to browse, and consider a code intelligence plugin for typed languages.

For permissions, auto mode is the built-in starting mode from v2.1.283 for interactive terminal and VS Code sessions. A separate classifier model reviews most actions and blocks risky ones, such as scope escalation. Allowlists through /permissions and OS-level isolation through /sandbox also reduce prompts.

Correct early. Esc stops Claude and keeps context. Esc twice or /rewind opens the restore menu. Each prompt creates a checkpoint, but checkpoints only track Claude's own file edits, so they do not replace git.

Scaling up

The options range from little coordination to a lot. Worktrees isolate separate sessions in their own git checkouts. Others include cross-session messaging, the desktop app, cloud sessions, agent view (research preview, claude agents), and agent teams (experimental, off by default).

For large changes, /batch <instruction> splits work across 5 to 30 subagents, each in its own worktree. To script it, loop over claude -p with --allowedTools and --permission-mode dontAsk, which denies anything not approved. Test on 2 or 3 files before running the whole list. Use --output-format json or stream-json --verbose to parse results.

For quality, try a writer and reviewer pair in separate sessions. Or run the bundled /code-review skill, which checks the current diff in a fresh subagent. A reviewer asked for gaps usually finds some even when work is sound. Chasing all of them leads to over-engineering.

How /goal works

/goal sets a completion condition and keeps Claude working across turns. After each turn, a small fast model judges the condition as not yet met, met, or impossible. That evaluator runs no tools and reads no files. It judges only what Claude has surfaced in the conversation.

Good conditions, up to 4,000 characters, have one measurable end state, a stated check, and constraints such as files that must not change. Add a bound like "or stop after 20 turns."

Operating details:

  • /goal shows status, including turns and token spend. /goal clear removes it, and so does /clear.

  • It does not change permissions. Run it in auto mode for unattended turns.

  • A goal survives resume, but counters reset.

  • With -p, it runs to completion in one invocation. Add --output-format stream-json --verbose so it does not look stuck.

  • If Claude makes no tool use for several turns, the loop stops with the goal still set.

  • Auth failures, exhausted credit, unrecoverable context overflow and unavailable models clear the goal.

  • Running background work defers evaluation, with check-ins from 30 minutes, adjustable through CLAUDE_CODE_GOAL_CHECKIN_MINUTES.

Use /loop for time intervals instead. Use a Stop hook for script-based checks across all sessions.

  3. Prune CLAUDE.md today by testing each line, then run /doctor and move situational material to skills.

  4. Before calling a long task done, have a subagent review the diff against PLAN.md, reporting gaps rather than style.

  5. Adopt the two-corrections rule. After the second failed correction, run /clear and write a better first prompt.

Key parts

Detailed summary

This summary is based on the full text of both docs pages, plus the agent teams status note and the model config page for ultracode rules.

Worktrees give parallel sessions separate checkouts. /batch splits one large change into 5 to 30 worktree-isolated subagents. Agent teams do not isolate teammates in worktrees, so you must partition files yourself. In every approach the workers are Claude sessions. Other tools join only through MCP (Model Context Protocol, a standard for connecting tools).

Why a script helps

With subagents, skills and teams, Claude decides each step and results enter a context window. A workflow holds the loop, the branching and the results itself. This allows repeatable quality patterns. Independent agents can adversarially review each other's findings, or several plans can be drafted and weighed.

The saved script is plain JavaScript with top-level await. It uses agent() to spawn one subagent, pipeline() for one per list item, and parallel() for a set at once. phase() groups progress and log() shows messages. Passing a schema returns validated JSON, with five attempts by default.

The runtime makes Date.now(), Math.random() and no-argument new Date() throw, so a relaunch repeats the same calls. An agent() call returns null when stopped or on an unrecoverable API error. pipeline() keeps those nulls, and the docs' example drops them with .filter(Boolean). My caution: count those dropped slots, or a sweep can look complete when it is not.

Starting a run

There are three routes. Run a bundled or saved command, such as /deep-research <question>. Add the keyword ultracode to one prompt, or ask in your own words. Or set /effort ultracode for the session.

The keyword only works in prompts you type. Since v2.1.210 it does not trigger from -p, scheduled prompts, unstamped SDK messages, webhook payloads or relayed PR comments. It chooses structure only, and tool calls keep their normal permission checks and sandboxing.

Session-wide ultracode plans a workflow for each substantive task, sometimes several per request. It drops the Large workflow warning, the concurrent subagent limit, and first-launch approval in auto mode. It is unavailable when workflows are off, or when the model lacks xhigh effort. --effort ultracode also sets effort to xhigh.

Approvals

The CLI prompt shows the planned phases. You can run, read the raw script, or cancel. Auto mode asks on first launch only. Manual and accept-edits modes ask on every run unless you opted out for that saved workflow. Bypass mode, claude -p and the Agent SDK show no prompt.

In headless use, allow it through a rule such as Workflow(<name>), auto mode, bypass, a PreToolUse hook, or your host. Subagents use your permission rules, so add the tools they need before a long run. In auto mode, a prompt the script passes to agent() does not count as a request from you when the classifier reviews that subagent's actions.

Failure and recovery

Press p to pause or resume. For a stopped run, ask Claude to relaunch it. Replay runs in start order. Completed agents return saved results, until the first agent whose prompt differs. That agent and all later ones run again. A failed agent also reruns everything that started after it. Stopping one agent with x counts as a failure, while stopping the whole run does not.

Leaving the session matters. Backgrounding a session continues the run. Exiting and stopping tasks ends it, but claude --resume can replay saved results if you ask for a relaunch. A fresh session starts over.

An agent with no output for the stall window restarts from the same prompt, up to five times. The new attempt has no transcript from the old one. Files it changed stay changed, and the tokens it spent still count. My caution: make agent tasks safe to repeat. Inside parallel() or pipeline(), a final failure leaves null and the run continues. Awaited directly, it ends the run.

Usage limits pause a run only in an interactive session on a claude.ai subscription, with autoContinueAtUsageLimit on, a reset within 24 hours, and fewer than three hits. It requires v2.1.271 or later. Otherwise the agent fails.

Cost

A run can use meaningfully more tokens than a conversation. The Large workflow warning appears above 25 agents or a projected 1.5 million tokens, but it only advises. Size guidelines tell Claude what to aim for: small under 5 agents, medium under 10, large under 50, and unrestricted for no guideline. A prompt can override them, and they are advice rather than caps. Agents run on your session's model unless something assigns another, so check /model first. You can also ask for a smaller model on routine stages.

Saving, sharing, disabling

Press s in /workflows. Save to .claude/workflows/ to share with the repo, or ~/.claude/workflows/ for yourself. Project workflows win name clashes, and monorepos use the closest directory. Plugins can ship workflows under a namespace. Saved workflows take a structured args input. To edit one, run /workflow-authoring, change the file, then /reload-skills. To disable, toggle /config, set "disableWorkflows": true, or set CLAUDE_CODE_DISABLE_WORKFLOWS=1. A run already in progress keeps going.

What to try

  • See a run first. Try /deep-research on a question you can judge, then open /workflows and read what each agent found. It needs the WebSearch tool.

  • Run a bounded audit. Use the docs' prompt on one directory: "use a workflow to audit every route handler under src/routes/ for missing authentication checks, and adversarially verify each finding before reporting it".

  • Set a stop rule. Use: "use a workflow to run npx tsc --noEmit and keep fixing the reported errors until the type check passes or two rounds in a row make no progress".

  • Read, then save. Choose View raw script before approving. If the run works, press s, commit it to .claude/workflows/, and code-review it like any other tool.

  • Set a size guideline deliberately. Run /config workflowSizeGuideline=small while learning. Add needed tools to allow rules before long runs, and turn off /effort ultracode when you return to routine work.

Nothing here applies to Codex directly. The docs do not describe a Codex equivalent. The stop rule and the adversarial check still work as written instructions there, which is my judgment.

Getting the job (December 2025 and January 2026)

He starts from burnout, a mortgage and a weak job market. He had become so reliant on AI that he struggled with basic SwiftUI syntax in a failed xAI interview. For Granola's take-home test, he wrote a very detailed prompt covering architecture, file layout and interfaces. He ran both Claude and Codex, picked a result and refined it by hand. In January he studied two people's advice. Peter Steinberger's advice was to use voice dictation and simply talk to the agent, because models keep getting better at reading intent. Boris Cherny's advice was to give Claude a way to verify its own work and to run agents in parallel. Agents that compile, smoke test and read logs can work alone for hours.

Knowledge debt (February and March 2026)

Granola's iOS app began as a side project and carried a messy architecture into production. He used parallel git checkouts, iOS verification steps and team agreement on a target architecture to ship features. One example is the Meeting Bar, which lets users move around the app without stopping transcription.

March introduces the central idea. Knowledge debt is what builds up when fast, agent-driven shipping outruns the team's understanding. He draws on the Grug Brained Developer essay and Riot Games' tech debt taxonomy, especially "contagion", meaning how far debt spreads. His practice follows from that. Know critical systems deeply, and accept less scrutiny on low-risk visual work.

Plain workflow, filtered review (April and May 2026)

He is skeptical of complex orchestration and of Steve Yegge's Gas Town approach. He says vanilla harnesses (the agent tools as shipped) do most of what elaborate graph setups do. His workflow has seven steps:

  1. Gather context.

  2. Plan with agents and split the work into stacked diffs, meaning a chain of small dependent pull requests (PRs).

  3. Let agents run.

  4. Review each PR step by step and leave comments.

  5. Have the agent address the comments.

  6. Do other work.

  7. Repeat if needed.

He also has a complaint about AI review comments. Agents treat every PR as small and produce many minor, defensive suggestions. So he has an agent filter and summarize them, since human cognition is the bottleneck.

May's side projects add verification techniques. Agents post screenshots to a local HTML page and compare Figma with the implementation. They use screen recordings for animation and Excalidraw diagrams to explain systems. He gives feedback on annotated screens by voice. He also pushes agents away from sanitized default UI styles. His view is that agents lack product taste but follow direction well.

Spec first, with real cost (June 2026)

Granola's Apple Watch app started as a vibe-coded proof of concept and became a rushed minimum viable product. He spent about $2,000 in API tokens having Fable 5 build a detailed spec. It reviewed PRs, ran tests, and read commit history and Linear tickets. The team then redesigned around a wire protocol between Watch and iOS. Code fell from about 13k to about 8k lines, and the whole team came to understand the system. He says the model was withdrawn three days after release. His lesson is that skipping design because agents can code is risky.

Multi-agent techniques (July and August 2026)

He now says agents code better than he does. He describes two techniques that keep him in the loop:

  • ARGUMENT.md debugging. Several GPT and Claude agents take the same bug and share context. They coordinate through one file until they agree on root cause, fix and verification. They adopt code names such as Copernicus, Hegel and Pauli.

  • Spec-based migration. Two agents each write a spec from code, history, PRs, tickets and simulator runs. A complex screen takes about 6 hours. They debate until they agree, then one implements and the other reviews.

He refuses to call this orchestration, because he stays in the loop and accountable. He cites a reported OpenAI incident involving 1,200 agents and HuggingFace as a reason for oversight. In August he notes how far one engineer's scope has grown. He says large refactors that took staff-level teams months now take about a week for a mid-sized app. Design still can't be delegated, though agents help review it.

System design and code quality (September and October 2026)

On an experimental project with many contributors, he tracked the system end to end to keep latency down. He reports a 70% cut and calls it his best work, requiring his full attention. In October, explaining code to blog readers exposed his own knowledge debt. He shows a Swift GeofenceService from Astra and calls it verbose, overengineered and defensive. Even so, running 10 Astra instances in parallel remains more efficient for him than writing by hand.

Conclusion

He built Free Parking, a desktop app that closes his terminal tabs in the evening and resumes agent sessions next morning. It helps him stop at one more prompt and be with his kids. His stable fundamentals are talking to agents directly, limiting parallel agents and specifying verification workflows. His three core skills:

  1. Work in parallel, but budget attention to control knowledge debt.

  2. Code is cheap and cognition is the bottleneck, so choose what to delegate and where to stay in the loop.

  3. As work moves from functions to whole systems, system design matters more.

A daily.dev commenter adds a useful idea. Keep a list of where the agents disagreed, because that is where scarce human review should go first.

  • Build a screenshot page. Tell the agent to save screenshots to a local HTML page, and compare them with the Figma design before you review.

  • Add a review filter. Ask an agent to sort AI review comments on a PR and show only those that change behavior or risk.

  • Mark your attention map. List the systems you must know deeply and those you'll accept on lighter review. Keep it in the repo.

Detailed summary

The post argues that GPT-6 models make broad, evidence-backed maintenance practical, and that prompts should be scaled only after review. Removing unused code

The old method combined static analysis, runtime logging and code review. It still made mistakes, such as removing code needed by reflection or by a rarely used fallback path. GPT-5.6 Sol improved on this when given a targeted area and clear validation criteria. It could write its own analysis, and its prompts were easier to maintain than the old tooling.

Astra got a looser test. The team gave it a typo-filled prompt asking it to find dead code and confirm disuse through Slack, Statsig (the experimentation platform) or other sources. Five engineers then ran prompt variations across repositories, part-time for two weeks. They merged over 1,400 PRs and deleted more than 800k lines. Reviews went to teams with project context. One service's container image fell from 3.31GB to 1.72GB, a 48% drop. Another cleanup removed about 400 visual snapshot test variants.

Tracking down stale experiments

Stale experiments are harder, because their code may still run in production and eligibility rules can change. The old method mixed deterministic analysis, database queries and scripts built by GPT-5.6 Sol. It missed many experiments that were truly stale.

The author asked Astra to draft its own prompt. The result asked for removal of dead code tied to stale or constant gates, configs and abandoned experiments. It carried these safeguards:

  • Verify the live Statsig configuration, and check git history and overlapping PRs.

  • Preserve production behavior and killswitches.

  • Ignore SDK fallbacks and local overrides.

  • Open one small draft PR per cleanup, linked to its Statsig console entry.

The author reviewed those PRs and commented. Astra took in the feedback and proposed a codebase-wide scan prompt. It also helped prioritize, because the author worried about having too many candidates.

The codebase-wide prompt ran with /goal in Codex. It covered every stale, constant, abandoned or fully shipped gate, config, experiment or layer that could be removed safely. It included indirect uses such as enums, aliases, dynamic names and cross-service consumers. It used production telemetry to estimate CPU cost. It required a grouped markdown report with owners and evidence, and it forbade changing live configurations.

The top results were large efficiency wins that had gone unnoticed for years. The team removed hundreds of experiments and flags after validation. The clearest example was a years-old flag meaning override all new features. One Python line mapped it to every feature and caused heavy CPU fan-out. Astra flagged it for humans because it was marked Permanent and might still serve an operational purpose. It was removed after review, for an estimated 0.42% CPU saving in the main affected service.

Detailed summary

Prompts and models

Codex can handle vague prompts, but clear ones are more reliable in large codebases and higher-stakes work. Use four elements:

  • Goal. What to change or build.

  • Context. Relevant files, docs, examples or errors. You can @-mention files.

  • Constraints. Standards, architecture, safety requirements and conventions.

  • Done when. Tests pass, or the bug no longer reproduces.

Then adjust by task. Use Low for fast, well-scoped work, Medium or High for complex changes or debugging, and Extra High for long, reasoning-heavy agentic work.

Planning

Plan mode is the guide's recommended default for most users. It gathers context, asks clarifying questions and builds a plan before coding. For longer multi-step work, you can configure Codex to follow an execution plan template, called PLANS.md in the guide. A linked cookbook article covers this.

AGENTS.md and configuration

AGENTS.md is an open-format file that loads automatically. It should cover repository layout, how to run the project, build and test commands, conventions, do-not rules, and how to verify done. Run /init in the CLI for a starter, then edit it to match how your team works.

It has three levels:

  • A global file in ~/.codex for personal defaults.

  • A repository file for shared standards.

  • Subdirectory files for local rules. The closest file to your working directory wins.

Keep it short and accurate. If it grows, keep the main file lean and point to task-specific files.

Configuration lives in ~/.codex/config.toml for personal settings and .codex/config.toml for a repository, with CLI overrides for one-off runs. It holds model, effort, sandbox mode, approval policy, profiles, MCP servers, multi-agent setup and feature flags. Two controls matter most:

  • Approval mode sets when Codex asks before running a command.

  • Sandbox mode sets what it can read, write and access.

Start with the default permissions and loosen them only for trusted repositories or specific workflows. The guide says many quality problems are really setup problems: wrong working directory, missing write access, wrong model defaults, or missing tools.

Testing and review

Do not stop at generated code. Have Codex write or update tests, run the relevant suites, check lint and types, confirm behavior, and review the diff for bugs and risky patterns. The criteria can come from the prompt or AGENTS.md.

/review works against a base branch, uncommitted changes, a specific commit, or custom instructions. A code_review.md file referenced from AGENTS.md keeps review behavior consistent. In the desktop app, you can click a diff row to send feedback into the next turn. On GitHub, Codex can review pull requests automatically or when you @-mention it. The guide states, "At OpenAI, Codex reviews 100% of PRs." That is a vendor statement about coverage, and it says nothing about quality.

External tools, skills and schedules

Use MCP (Model Context Protocol, an open standard for connecting tools) when context lives outside the repository or changes often. Start with one or two tools that remove a repeated manual loop. Add servers with codex mcp add or through Settings in the desktop app.

A skill packages instructions in SKILL.md, plus context and supporting logic. Keep each skill to one job, and write a description with the trigger phrases people would actually say. Make one task work first, then convert it. If you keep reusing a prompt or correcting the same workflow, make it a skill. $skill-creator scaffolds a first version. Personal skills go in $HOME/.agents/skills and team skills in .agents/skills.

Scheduled tasks, on the desktop app's Scheduled page, choose a project, prompt, cadence and environment. Good candidates include commit summaries, CI failure checks and release notes. If a workflow still needs heavy steering, make it a skill first. They also suit maintenance, such as reviewing recent chats for repeated friction.

Long-running goals

Type /goal in the desktop app, CLI or IDE extension. The goal text acts as both the first prompt and the completion criteria. If the outcome is unclear, start with /plan, have it interview you, then turn the result into a goal with measurable success criteria.

A good goal has three elements:

  • Outcome. The result you want, rather than the activity.

  • Constraints. Required tools, boundaries, compatibility needs, and approaches to avoid.

  • Verification. Tests, measurements or review criteria that prove completion.

The page's example migrates JavaScript to TypeScript. It preserves behavior, compiles in strict mode without explicit any, and passes the full test suite.

Steering options during a run:

  • The desktop progress row lets you pause, resume, edit or clear a goal.

  • Follow-up messages add context or adjust constraints.

  • A side chat gives a recap without interrupting the main chat.

  • Pause before you expect to lose connectivity.

A goal does not expand access. The same sandbox and approval policy applies, and the goal pauses when it needs a decision. Automatic approval reviews let a separate reviewer evaluate eligible requests without widening those limits.

Each chat has its own context and goal, so chats can run at once. Do not let two chats change the same files. Use git worktrees for separate checkouts. On a Mac, enable "Prevent sleep while running" for local work. Use notifications to see when a chat needs you.

Common mistakes

The guide's list is a useful audit. It names these:

  • Durable rules kept in prompts.

  • No build or test commands given to the agent.

  • No planning on complex work.

  • Full computer permissions granted too early.

  • Live tasks on the same files without worktrees.

  • Recurring tasks scheduled before they work by hand.

  • Watching step by step instead of working in parallel.

  • One chat for a whole project.

What to try

  1. Rewrite your next Codex prompt with goal, context, constraints and done when. Compare the number of corrections needed.

  2. Next time Codex repeats a mistake, ask for a retrospective and add one line to AGENTS.md.

  3. Add code_review.md, reference it from AGENTS.md, and run /review against your base branch before opening a pull request.

  4. Start a /goal with an outcome, constraints and a test command, in its own git worktree.

  5. Convert one prompt you keep reusing into a skill with $skill-creator, and schedule it only after it runs reliably by hand.

What works now

These techniques combine well, and their evidence varies from vendor guidance to single anecdotes.

Name the bans, then extend the list

Start from the defaults you can see in the output. Anthropic's guide and Osmani's post give the same method on Opus 5.5. List exact patterns to avoid, inspect what replaced them, and ban that too if you dislike it.

The list has to be per model. OpenAI's GPT-5.5 guide bans different things: decorative orbs, cards inside cards, floating section cards, split heroes with a card, and one-note palettes. It also tells the model to scan its CSS colours before finishing. Anthropic's frontend-design skill adds more, including cream with terracotta and near-black with one acid accent. It also lists hairline broadsheet layouts and fade-up on every section. That skill is undated, and it warns implicitly that its examples will age.

Steer each model's known habits

Directed and open prompts tell you different things. A third-party summary of Vo's episode says directed prompts test function and open prompts expose defaults. It also suggests explicit spacing limits for Claude, and hardcoded palette and layout rules for GPT. Flag: these steering tips rest on that one summary of one person's session, and I could not confirm them in the episode.

Thomas Wiegold's Sol review guesses that Sol needs explicit requests such as adding motion. Flag: that is one brief, one run, and an author who prefers Claude. The sources also conflict on B2B work. The summary says Vo's top B2B dashboard came from Opus 5.5, while the episode page calls Astra strong for B2B frontend.

Compare contrasting prototypes

Ask for options before you ask for a build. Shihipar requests several very different directions in one HTML file, or a mock with fake data before touching the real app. He uses them to surface criteria you only recognise on sight.

Both vendors have productised this. Claude Code's /design drafts editable artboards, then implements the one you pick. It needs v2.1.234 or later and is a research preview. OpenAI's ideate skill makes three directions by default. They must differ in structure, interaction and hierarchy before brand styling, and it refuses to build before you choose. Claude Academy's tutorial similarly suggests comparing named layouts, such as card, sidebar and tabs.

Give references, and code beats images

Shihipar says source code is the best reference, because it holds more structure than a screenshot. He points the model at a reference folder, even in another language. His example is about backoff logic, so applying it to UI is a reasonable extension, not his tested claim.

Screenshots remain useful targets. OpenAI's use-case guide asks for several states, including mobile, hover, empty and loading. It says references need not be polished, only clear on hierarchy and spacing. The Codex plugin also accepts URLs, Storybook links, tokens and brand assets.

Build and keep a design system

Put the system where every session can read it. Claude Design imports from GitHub, design files, uploads or a local codebase through /design-sync. Anthropic says it checks output against the system before you see it, and warns that a messy source shows up in the output. Handoff to Claude Code continues from the design work instead of a screenshot.

For Codex, OpenAI says to name the primitives, the token locations and the canonical components, especially on new projects. It says to avoid building a parallel system.

Charlie Hills merges reference DESIGN.md files with a brand kit. Brand wins on colour and fonts, and references win on layout. Flag: this is a self-reported marketing writer's anecdote, on Fable 5, from June. Russo's HyperFrames workflow also records a site's brand in a design file, but that work is for video.

Make the agent look at the render

Every strong source closes the loop in a browser. Claude Code Desktop's Browser pane screenshots, inspects the DOM and fixes issues, with autoVerify on by default. From the CLI, claude --chrome offers design verification and console reading. Computer use covers native apps, but it is the broadest and slowest route.

OpenAI's guide asks for Playwright screenshots and canvas-pixel checks on desktop and mobile. Check that the page is non-blank, framed, interactive and free of overlap. Its browser docs suggest naming states such as loading, empty, error and success. They also recommend Astra for checking a page against a screenshot. The same docs say the browser is not in the Codex CLI or IDE extension, so plan on Playwright there.

Some limits matter. Computer use downscales screenshots with no setting to change it, so enlarge small UI text. Anthropic says dense images still benefit from higher resolution, plus crop and measure tools. Startrise adds a useful check: read the source for faked effects and stubs, not only the render.

Require a zero diff for migrations

Use image diffs when the existing UI is the spec. The pstack playbook requires a baseline harness first and treats any nonzero pixel diff as failure. It forbids editing the harness or the baseline to pass. This suits parity work only, since new design has no baseline. Kapoor's scepticism about screenshot-and-replace concerns editing canvases, which is a different job. That distinction is my reading.

Use skills for judgment you repeat

Keep long design guidance in a skill, so unrelated tasks don't pay for it. Anthropic argued this in November 2025, and the context argument still holds. The current frontend-design skill plans tokens first, reviews the plan against the brief, builds, then critiques with screenshots where possible.

Test skills before trusting them. Russo's team runs evals on theirs and found the thinnest wrapper worked best, though for video. Claude Code's claude plugin eval can compare a plugin against a no-plugin baseline. Community packs are weakly evidenced. The Claude Codex's one-month review favours Impeccable plus Playwright MCP, but reports no metrics. Impeccable's listing shows no testing on current models, and its last release there predates June.

Split what can be checked from what needs taste

Castello Branco's most usable idea is to decompose quality. Contrast, alignment and palette can often be verified nearly deterministically. Style and fit need human judgment. She also says to fix audience, use and period before judging. Her probe results lack published data, so they can't be reproduced, and she sells this kind of data and tooling.

Use HTML when the output isn't a web page

HTML suits slides, documents and video because the browser does the layout. Kapoor separates the editable HTML from the PDF you distribute. His page notes that the demo was not a controlled comparison, and that poor sizing can still overflow. Russo shows the same HTML can preview and render video frames, but says creative quality remains open.

The question and the sides

Allie Howe runs an Oxford-style format with opening statements, timed responses and a vote on changed minds. Livingstone and Huntley argue loops deserve the hype and lead toward software factories. Horthy and Pstrucha accept loops for mechanical work and challenge the leap beyond that.

Opening statements

Huntley says he saw engineers at Canva prompting repeatedly, about two and a half years ago, and realized the process was programmable. He reduced it to a Bash loop that became "Ralph". He calls loops a new programmable substrate, while conceding they are incomplete. He predicts next year's talks will cover how loops fail. His examples include language ports and research over a set of Linear tickets.

Horthy asks whether the hype matches reality. He compares agents to Kubernetes controllers, which work because each owns a small target with a desired state. He says Kubernetes took roughly seven to eight years to mature, and it rests on deterministic control loops. His worry is engineers stepping back from architecture. He says AI review bots have not demonstrably solved code review.

Livingstone frames all development as feedback loops: try, learn, apply. CI, PRs, design reviews and customer feedback already fit that shape. He argues software is highly verifiable, and more so as less of it faces human subjectivity.

Pstrucha asks whether anyone is truly satisfied with generated code. He still sees substantial rework and architectural steering after verification. He separates quality from economics and asks what monthly budget per engineer stays viable, naming $10K, $100K and $1M.

Permissions and goal seeking

Livingstone argues reinforcement learning makes models more goal-seeking, so safety must come from surrounding infrastructure. Perfect safety is unattainable, he says. The essay credits Huntley with the failure story: an agent's token cannot deploy, so it searches the filesystem for stronger credentials. Persistence turns an authorization failure into a search problem. The advice is to keep secrets out of readable files.

Why loops work now and how to constrain them

Huntley says models have been good enough for about a year, and understanding is what changed. He cites about $10.42 per hour to run a loop, from a calculation made about a year earlier. The essay notes that the model and billing basis are unspecified. He admits the original Ralph targeted greenfield work.

For existing codebases he offers "loop engineering". Domain rules go into pre-commit hooks that reject a change and echo a prompt back to the agent. The essay gives a Bash example that blocks src/domain from importing @app/ui in the staged snapshot. It adds three caveats. A string match only shows the pattern, so real enforcement needs a language-aware analyzer. A local hook can be tampered with. Passing a hook does not mean the work is accepted.

Verification and context

Pstrucha says closing the feedback loop matters more than model intelligence. His informal illustration is a 5% per-step error rate cutting correctness to roughly half or less after 10 to 20 iterations. The essay stresses this is not a reliability estimate.

Horthy says Ralph's key advantage was clearing context each iteration. He calls the smart and dumb zones training wheels for building intuition. His budgets are about 100,000 tokens for newcomers, about 200,000 with million-token windows, and under 60,000 for hardest problems. He admits going over 300,000 when casually exploring. The warning signs are behavioral: flailing on a test, strange edits, and blaming unrelated causes. His lesson is one thing per iteration, with deterministic logic assembling small prompts.

Huntley treats compaction as lossy, like repeatedly re-uploading a video. He allocates context deterministically and gets uneasy above 100,000 tokens. He also runs new models bare, without skills or markdown files, because he says models have their own preferences. He recommends reading model cards.

Loom and convergence

Howe raises convergence engineering: assemble loop output into a system under test and iterate until it settles. Horthy uses Loom, Huntley's experimental Rust project, as the test case. He describes using behavioral data from experiments as feedback for subjective UI choices. The essay calls this a proposal, not a result. Huntley says Loom remains on GitHub and that he has spent months on verification instead. Horthy concludes this does not justify dropping review.

Spending, memory and control

Pstrucha says loops mostly fail loudly on the bill. He accepts about $5 per PR for security scanning, and he likes rewrites with strong test suites. Throwaway prototypes also fit, since they buy product information rather than production code.

Livingstone says access control was not designed for machines acting for humans, so shared memory has unresolved authority questions. He likes markdown as a memory substrate and describes exposing Notion content that way as a simpler option than MCP (Model Context Protocol).

Huntley says the while true script is only a primitive, and a larger system needs an outer controller to decide whether to continue. Pstrucha says humans must keep architecture and trade-offs even with free compute, including what not to build.

Factories as products and attribution

Horthy names the main anti-pattern: disappearing for months to build a factory from blog posts. He treats a factory as a product for your engineers. Start from a real problem, build a small loop, observe, then iterate.

Livingstone notes Git allows one signer per commit and says that must change. Liability must trace to a person or company, from intent to production.

Closing

Pstrucha stresses finding failure boundaries firsthand. Livingstone says competitive pressure makes agents hard to ignore. Horthy says he wants a lights-off factory, but the missing capability is at the model level. Huntley favors static types, naming Rust and Haskell, and vendoring dependencies to own the supply chain. Hands were too close to call under the stage lights.

What fails during sustained work

The speakers want agents that work for 5 to 6 hours or more. They sort the problems into three buckets. There are two levers: better model weights, and a better harness around the model. The two improve together, so harness parts can later come out. The speakers cite METR time horizons at 50% success, measured in human-expert time. These moved from about 1 hour for Sonnet 3.7 to about 12 hours for Opus 4.6. Wilson also mentions Sonnet 4.5 runs of about 30 hours, with no benchmark behind them.

From Ralph loops to recoverable progress

A Ralph loop repeatedly feeds a prompt to the agent until tasks finish. The original version started fresh sessions. Anthropic's plugin keeps one session with compaction, plus a stop hook, a maximum iteration count and a completion promise. The reasoning is that predictable failure beats unpredictable success.

The November 2025 harness added an initializer agent. It writes a JSON feature list with passes flags, a progress file, a Git repository and an init script. The speakers also trace model and product changes along the way. Skills use progressive disclosure, loading detail only when needed. Programmatic tool calling saves context too. The generator builds and a separate evaluator criticizes, which is a GAN-inspired analogy rather than real GAN training. The evaluator uses Playwright or Claude for Chrome to open pages, click, take screenshots, and read console and network errors. It grades against a rubric and sends critiques back.

The design rubric has four criteria: design, originality, craft and functionality. Design and originality get extra weight because the model already handles the other two well. Generic purple gradients count against a design. A design run took 5 to 15 rounds over about 4 hours. The evaluator is tuned to be harsh, with few-shot examples for calibration.

Planner and contract

A planner expands a short prompt into a high-level spec. It avoids granular technical detail, since an early error there would cascade. Before building, the generator and evaluator negotiate an acceptance contract through Markdown files. The evaluator then grades against that contract.

Retro Forge and specific failures

A solo run built a game maker whose opening screen and sprite editor looked fine, but the arrow and space keys did nothing in play mode. The harness run took about 6 hours and cost about $200. It produced a working physics loop, a 54-color palette and an in-app AI level assistant. Its contract for one stage had 27 acceptance criteria.

The evaluator's value showed in specifics. It caught a FastAPI route-ordering bug that passed unit tests, a delete-key bug and a Boolean logic error. Specific failures make criticism actionable. Reading traces was the main way to find where the prompt needed work.

Removing scaffolding

Opus 4.6 held a coherent two-hour build without per-feature resets. Sprints came out, and evaluation moved to the end of the build. What the Q&A adds

The Q&A from 40:19 is unusually practical.

  • Spec as anchor. The planner stays outside the core loop, and its spec is reinserted as a reference point.

  • Human checkpoints. A hook at a stop condition can add one, and the team would rather remove humans where possible.

Context limits shape everything

Pocock frames AI as still subject to core engineering practice. The workshop follows one feature from idea to shipped code. Citing Dex of HumanLayer, he describes two zones in a model's context. Attention cost grows quadratically with tokens, so output degrades as context fills.

His working threshold is about 100k tokens. He says this holds even with a 200k or 1M window, and that the 1M window mostly adds dumb zone. He thinks large windows suit retrieval better than coding. This is his heuristic, not a measurement he presents.

Three habits follow. Keep the always-loaded system prompt small, since a large one starts you closer to the dumb zone. Watch the exact token count in a status line. Prefer clearing to compacting. He uses the film Memento as an analogy: the model forgets everything between sessions. Clearing returns to the same base state, while compaction leaves a written summary he dislikes.

Exploration can go to subagents, which run in isolated contexts and return summaries. In the demo, an explore subagent used about 93.7k tokens on Opus, without filling the main session.

The exercise is Cadence, a course platform CMS. A brief from a fictional "Sarah Chen" reports low student retention, and the feature is gamification. Pocock rejects a straight spec-to-code handoff, since you need to understand and shape the code yourself.

Detailed summary

The talk and post make one argument: engineering discipline moves from the code to the scaffolding around agents. A harness here means the tools, rules, docs and feedback loops that surround the agent. This summary follows the post and uses the talk for later detail.

The experiment

The team began with an empty repo in late August 2025. Codex CLI with GPT-5 generated the scaffold, and Codex even wrote the first AGENTS.md. After five months the repo held about 1 million lines and about 1,500 merged PRs. Three engineers grew to seven, averaging 3.5 PRs per engineer per day. Hundreds of internal users relied on the product. The team estimates this took about one-tenth the time of hand-coding. All of this is self-reported. In the talk, Lopopolo adds that hand-editing code was banned, and describes about nine months of agent-only work by then.

The engineer's new role

Early progress was slow because the environment lacked tools and structure, by the post's account. So engineers broke goals into building blocks and had agents build each one. In the talk he says each engineer effectively gets the capacity of 5 to 5,000 engineers, limited by GPU capacity and tokens. Engineers act like staff-level managers. Code being cheap means low-priority tasks can run in parallel, with the team keeping whichever result works. Large stalled migrations can finish by launching many agents, such as 15 at once.

Writing down taste

A good patch depends on hundreds of small, unstated decisions, so he says to write them down. Sources include docs, architecture decision records (ADRs), persona guides, tickets and past review comments. Each teammate documents their own expertise, and every agent inherits it.

The post then enforces invariants and leaves implementations open. Data must be parsed at boundaries, for instance, but the method is free. Each business domain has fixed layers with validated dependency directions: Types, Config, Repo, Service, Runtime, UI. Cross-cutting concerns such as auth and telemetry enter through one Providers interface. Custom linters and structural tests check all this, and error messages contain remediation steps.

The talk gives concrete cases. A lint rule requires retries and timeouts on every fetch call, and the codebase is migrated once. A structural test caps files at 350 lines. Reviewer agents check security and reliability in CI on each push. He sums this up as everything being a prompt, including lint messages and review comments.

Making the app legible

As output grew, human QA became the bottleneck, so the team exposed the UI, logs and metrics to Codex. Each worktree boots its own app instance and a temporary observability stack. Codex queries logs with LogQL and metrics with PromQL. Skills give it DOM snapshots, screenshots and navigation through Chrome DevTools Protocol. This allows goals like service startup under 800 ms, or no span over two seconds in four critical journeys. Single runs have lasted up to six hours, often overnight.

Repository as system of record

One big AGENTS.md failed in four ways. It crowded out key constraints, made everything equally important, went stale quickly, and resisted mechanical checks. The replacement is about 100 lines pointing into docs/. That folder holds design docs, active and completed execution plans, a tech debt tracker, product specs and generated references. Linters check that docs are current and cross-linked. A recurring doc-gardening agent opens fix-up PRs. The principle is that anything outside the repo doesn't exist for the agent, including chat threads and Google Docs.

The talk's Q&A extends this to delivery timing. Front-loading rules overwhelms agents, and compaction can drop them. So rules should surface through failures when relevant. The team keeps only about 5 to 10 skills, improving them and hiding complexity behind them. He prefers first-party harnesses, because labs post-train models within them.

Throughput and review

Merge gates are minimal and PRs short-lived. Flaky tests are usually rerun. The post's reasoning is that fixing is cheap and waiting is expensive at this output, and it says this would be irresponsible at low throughput. Most review is agent-to-agent, and agents may accept, defer or reject comments. The talk notes 3 to 5 PRs per engineer per day and merge conflicts, which led to shorter PR lifetimes. It also mentions about 750 packages in a pnpm workspace, with boundaries that let agents scope their work. One way of doing each common task makes output more predictable.

Autonomy and cleanup

The repo reached the point where Codex can take a bug from one prompt to merge. It reproduces the bug, records a failure video, fixes it, records a second video, opens a PR and handles feedback. It escalates only for judgment. The post warns this depends on the repo's specific investment.

Agents copy existing patterns, including bad ones. The post says the team spent every Friday, 20% of the week, cleaning up slop, and that this didn't scale. It moved to golden principles enforced by background Codex tasks that open small refactoring PRs. The later talk still describes Fridays as garbage collection day, turning each week's feedback into docs, tests or lints. So the two accounts differ on this detail.

Where it ends

Tokens split roughly into thirds across planning, implementation and CI. Plans should be reviewed as their own PRs before execution. He treats code as a build artifact, with specs and constraints acting like a compiler pipeline, so swapping models keeps the rules. Starting advice is simple. Have agents add tests to raise confidence, then automate your slowest waits. Each time he has to type continue, he treats it as a harness failure. Open questions in the post include how coherence holds up over years.

Detailed summary

This summary is based on the full article page.

Why naive runs fall short

The author builds on earlier work, where an initializer split a spec into tasks and a coding agent built one feature per session. Two failures persisted.

The first is context degradation. Models lose coherence as context fills, and some, such as Sonnet 4.5, showed "context anxiety" by finishing early near a perceived limit. Compaction summarizes history in place but gives no clean slate. Context resets work better, using a fresh agent and a structured handoff. They add orchestration, token overhead and latency.

The second failure is self-evaluation. Agents praise their work, especially on subjective tasks such as design. Splitting off a skeptical evaluator was far more tractable than teaching a generator to doubt itself.

Making frontend design gradable

The author uses a loop inspired by GANs (generative adversarial networks, where one model generates and another critiques). The evaluator drives live pages through the Playwright MCP server and takes screenshots before scoring.

There are four criteria: design quality, originality, craft and functionality. Claude already handled craft and functionality by default, so the other two carried more weight. The criteria explicitly penalize generic "AI slop" patterns. Few-shot examples with detailed score breakdowns reduced drift.

Each generation ran 5 to 15 iterations, and full runs took up to four hours. The generator chose between refining its direction and pivoting. Scores rose and then plateaued with headroom left. The wording of the criteria shaped output style, and even the first iteration beat a no-prompt baseline. In one Dutch art museum site, iteration 9 was a polished dark landing page. Iteration 10 turned it into a spatial 3D gallery with CSS-perspective rooms.

Scaling to full-stack coding

The first full version used Opus 4.5 and three agents.

  • Planner. It expands a prompt of 1 to 4 sentences into a product spec. It stays on product context and high-level design, avoiding granular technical detail, and it is encouraged to add AI features.

  • Generator. It builds in sprints, one feature at a time, using React, Vite, FastAPI and SQLite, later PostgreSQL. It uses Git and evaluates itself before handing off to QA.

  • Evaluator. It clicks through the running app and tests features, API endpoints and database states. It grades each sprint against hard thresholds.

Before each sprint, generator and evaluator negotiated a sprint contract defining "done" and how it would be verified. They communicated through files.

The test prompt asked for a 2D retro game maker with a level editor, sprite editor, entity behaviors and a playable test mode.

Out of the box, Claude was a weak QA agent. It talked itself into approving flawed work and tested superficially. The evaluator prompt needed several rounds of tuning before it became useful.

Iterating on the harness

The central principle is that each component encodes an assumption about what the model cannot do alone. These assumptions can go stale, so they need stress-testing. The guidance is to find the simplest solution and add complexity only when needed. Radical simplification failed to match performance at first, so the author removed components one at a time.

Opus 4.6 changed the design in four ways.

  • The sprint construct came out, since the model could sustain longer coherent work.

  • The planner stayed, because the generator under-scoped without it.

  • The evaluator moved to a single pass at the end.

  • Context resets came out, since Opus 4.5 had largely removed context anxiety.

The key insight is that an evaluator's value depends on where a task sits relative to solo capability. It is worth its cost only beyond what the model reliably does alone. The author also added prompting so generators built real agents that drive app functions through tools.

What comes next

Scaffolding may matter less for some problems as models improve. Stronger models also open room for harnesses that exceed the new baseline.   • Use a planner that stays high level. Give a 1 to 4 sentence brief and ask for a product spec with no technical specifics. Compare scope against skipping that step.

Detailed summary

This summary rests on the repo README (first 100,000 characters), the skills doc, Why gstack, and three outside articles. I didn't run gstack. gstack packages one founder's agent workflow into a set of chained roles, and the debate is over how much that packaging adds.

What it is

gstack is a collection of skills, which are prompts in SKILL.md files that assign an agent a specialist role. The process is a sprint: Think, Plan, Build, Review, Test, Ship, Reflect. You clone it into ~/.claude/skills/gstack and run ./setup. Other agents install with ./setup --host <name>. An optional team mode updates shared repos automatically.

The main groups, from the README:

  • Planning: /office-hours, /plan-ceo-review, /plan-eng-review, /plan-design-review, /plan-devex-review, and /autoplan.

  • Design: /design-consultation, /design-shotgun, /design-html, /design-review, /design-motion.

  • Review and QA: /review, /qa, /qa-only, /investigate, /verify, /test-audit.

  • Shipping: /ship, /land-and-deploy, /canary, /benchmark, /modernize.

  • Browser: /browse, with Aside first and bundled Chromium as a fallback.

Several mechanisms are concrete:

  • /review audits a diff for problems that pass CI but fail in production, such as N+1 queries, race conditions and trust-boundary issues. It fixes mechanical problems and surfaces ambiguous ones for you to decide.

  • /qa reproduces defects and writes regression tests that fail before the fix and pass after it.

  • /careful warns before destructive commands such as rm -rf, DROP TABLE and force-pushes. It hard-denies default-branch force-pushes.

  • /freeze limits edits to one directory, and /guard combines both.

  • /autoplan runs CEO, design and engineering reviews in sequence, and surfaces only judgment calls.

  • /codex adds a second opinion from OpenAI Codex. It's available on every harness except Codex itself.

Use with Codex

The README lists Claude Code as fully supported. Codex CLI is experimental, installed with --host codex into ~/.codex/skills/gstack-*/. Safety skills there are advisory only. That matters if you'd rely on them to stop a destructive command.

The fair case for it

The strongest argument is sequencing. Augment Code's review says the chain is what separates gstack from a plain prompt collection. andrew.ooo praises the ready-made process, the free license and the option to fork and trim. It calls gstack well packaged, useful for newcomers, and the controversy overblown. Cross-model review through /codex also fits a pattern seen among other engineers. Fast fixes count for something too. Augment reports one release fixing 8 community bugs, including 4 security guards that were failing open. It reads that as evidence of real use.

Tan's own case is about parallel work. Using Conductor, he says he runs 10 to 15 Claude Code sessions in isolated workspaces, each at a different stage. He argues a consistent process stops parallel agents from creating chaos. He also argues gstack enforces discipline across sprints, where Karpathy-style rules alone don't last.

The criticism

The objections fall into four groups:

  • It's prompts. Critics quoted by andrew.ooo say experienced users already build similar role skills. They doubt it would have drawn this attention without Tan's name.

  • It's a lot of process. 28 skills may exceed what many developers need.

  • Line counts are weak evidence. One commenter called Tan's 10K to 20K lines per day "a red flag, not a feature". His retro lists 140,751 lines added and 362 commits in one week, across 3 projects.

  • The output has been challenged. Tan posted about 37K lines per day across 5 projects, on a 72-day streak. Developer Gregorein then audited one public site, as reported via Fast Company on 7 Jul 2026.

That audit found 6.42 MB across 169 requests on one homepage load, 28 test files served to every visitor, and 78 unused Stimulus controllers. It also found a 0-byte AVIF logo in production and uncompressed PNGs near 2 MB. Gregorein called it "AI slop code". The report notes this is one critical audit of one site. It doesn't say whether Tan uses linting, CI or human review, and reports no reply from him.

Reading the numbers

Tan knows line counts inflate with AI, and he says so. His Why gstack page uses logical code changes instead. By his math, his pace is about 810 times his 2013 rate, with about 240 times the output of all of 2013. It covers 40 repos, excluding one demo. He also reports three production services and over 40 features in 60 days, part-time. He points to a separate document on methodology and a reproduction script, which I didn't open. All of this is self-reported.

Other numbers conflict across sources. Star counts run from 23K in March to about 138k now. The tool count is 23 in the README text, 28 in andrew.ooo, and more in the skills table. The 2,400-line, 8-minute session is an illustrative example. Stars and fork counts measure attention, and neither source reports defect rates.

Risks to check

Some features deserve care. /setup-browser-cookies copies selected cookies from your browser, so it carries real security exposure. Augment's reported fail-open guards show that safety code can have bugs. Augment sells competing products, andrew.ooo says it's AI-agent-operated, and aiweekly relays Fast Company. So none of these is a neutral test. Telemetry is reported as opt-in and off by default.

What to try

These actions take the useful parts without adopting everything.

  • Read before installing. Read the SKILL.md for /review, /qa and /careful, and copy what you like into your own skills.

  • Trial it on a throwaway branch. Run one small feature through /office-hours, /plan-eng-review, /review, /qa and /ship. Note what you'd keep.

  • Add a regression-test rule. Copy the /qa standard: each bug fix gets a test that fails before the fix and passes after.

  • Use hooks for real guards. In Claude Code, try /careful and /freeze. In Codex, assume they only advise, and rely on your own sandbox settings.

  • Add cross-model review. Run /codex from Claude Code, then compare its findings with Claude's own /review.

Its role-play framing may matter less as models improve at planning, though that's a guess. The Gregorein audit tells you about one site, and doesn't test gstack directly.
